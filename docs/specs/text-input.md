# 仕様: テキスト入力による字幕送信

> **状態: 実装済み**（通話中の入力欄、IMEガード、Escの競合回避、通話ログの`[入力]`マーク）

## 目的

音声認識が止まったとき、あるいは固有名詞・数字のように
認識が崩れやすい語を伝えたいときの逃げ道として、
キーボードから直接テキストを送れるようにする。

音声の代替であって、チャット機能ではない。
送信したテキストは音声発話とまったく同じ扱いで、
同じ吹き出しに表示され、同じ経路で翻訳される。

## 対象ファイル

`call.html`

## UI

### 入力欄

- 通話中は常時表示する。音声が止まった瞬間にすぐ打てることが重要なので、
  ボタンで開閉する方式にはしない
- 字幕エリアの下部に固定する
- 字幕エリアを圧迫しないよう、高さは最小限（1行ぶん）にする
- 接続前・切断後は表示しない

### プレースホルダ

UI 言語に合わせて切り替える。i18n オブジェクトにキーを追加すること。

- 日本語: `音声が届かないときはここに入力`
- 韓国語: `음성이 안 들릴 때는 여기에 입력`

「チャット」とは書かない。この機能の目的が一目で伝わる文言にする。

## 入力の挙動

### 送信

- `Enter` で送信
- `Shift + Enter` で改行
- 送信後は入力欄をクリアし、フォーカスは維持する
  （連続して打てるようにするため）
- 空文字・空白のみの場合は送信しない

### IME（日本語・韓国語入力）のガード

**これが最も踏みやすいバグ。** 日本語入力では変換確定に `Enter` を使うため、
ガードがないと「こんにちは」の変換確定で送信されてしまう。

`keydown` ハンドラの冒頭で以下を必ず入れる。

```js
if (e.isComposing || e.keyCode === 229) return;
```

`keyCode === 229` は一部ブラウザで `isComposing` が立たない場合の保険。

### Esc キーの競合回避

現在、`Esc` は「直前の自分の字幕を削除する」に割り当てられている。
入力欄にフォーカスがあるときにこれが発火すると事故になる。

- 入力欄にフォーカスがあるとき、`Esc` で字幕削除を発火させない
- 入力欄での `Esc` は、入力内容のクリアに割り当てる
  （入力が空なら何もしない）

## 翻訳経路

送信テキストは、音声の確定テキストとまったく同じ経路を通すこと。
別経路を作ると、テキスト入力のときだけ品質が落ちる。

以下がすべて適用される状態にする。

1. `glossary.md` による誤認識補正
2. `fixed-phrases.md` による定型フレーズの即答
3. `worker/names.json` による固有名詞の表記固定
4. 直近 6 発話の会話文脈の付与
5. 短文は Azure、長文は Workers AI というエンジン振り分け

既存の `handleFinal` 相当の処理を呼び出す形にして、
翻訳ロジックを二重に実装しないこと。

## 表示

- 送信したテキストは、自分の吹き出しとして音声発話と同じ形式で表示する
- 相手にも同じ形式（`subtitle-final` → `subtitle-translated`）で送る
- 相手側から見て、音声かテキストかの区別は不要

## 通話ログ

- テキスト入力で送った発言も、音声と同じく通話ログに記録する
- ただし後から見返したときに区別できるよう、`[入力]` のような
  短いマークを付ける
- 既存の `deleteLogEntry` との整合も取ること
  （× や Esc で消したらログからも消える）

## やらないこと

- 相手にタイピング中であることを通知する機能
- 送信済みテキストの編集
- 履歴の呼び出し（上キーで前の入力を戻すなど）

## 確認方法

1. 日本語で「こんにちは」と打ち、変換確定の `Enter` で
   誤送信されないこと
2. 送信すると自分の吹き出しに表示され、相手にも届くこと
3. 「うん」と打つと `fixed-phrases` が効いて即座に `응` が出ること
4. 「私の名前は山田だよ」と打つと `내 이름은 야마다야` になること
   （`names.json` が効いていることの確認）
5. 入力欄にフォーカスがある状態で `Esc` を押しても、
   直前の字幕が消えないこと
6. 通話ログに `[入力]` 付きで記録されること
